# keel security audit: evidence appendix

Raw verification records behind [REPORT.md](REPORT.md), in English as written by the verifiers. Audited commit: `8037faf` (main), 2026-10-29. Every entry was found by a first-round auditor and then re-checked by an independent adversarial verifier against the release builds on 127.0.0.1 (macOS), except entries marked "found in round 2", which the round-2 agent reproduced itself and the lead auditor spot-checked. Script paths in the reproduction notes point into a temporary scratch directory and will not survive the session.

## H1. Anonymous GET /dl/{name} buffers the whole node binary in memory per request with no streaming/timeout/cap; stalled downloads OOM the master

- **Severity:** high · **Verdict:** confirmed · **Default config affected:** yes
- **Severity change:** unchanged (high)
- **Attacker:** anonymous-internet; no auth, no token. Precondition: the admin has placed keel-node-linux-amd64/arm64 in DATA/dist, which the documented install flow (install.sh fetches $MASTER/dl/keel-node-linux-$ARCH, README:128) requires for any deployment that installs nodes. Empty dist => cheap 404, no memory.
- **Locations:** `master/src/main.rs:213`, `master/src/main.rs:208-217`, `master/src/main.rs:260`, `master/src/main.rs:286-296`, `master/install.sh:38`, `README.md:128`

**Summary.** download() (main.rs:208-217) does tokio::fs::read of the full binary into a Vec and hands it to the response body; the route is on the outer router (main.rs:260), reachable with no auth (confirmed 200 anonymously). hyper holds the buffer until the body is fully written, and serve_tls sets no write/idle timeout (no timer) and no connection cap, so a client that requests the binary and never reads pins ~one binary's worth of RAM per connection indefinitely. Reproduced: 20 stalled 10 MB downloads took the release master's RSS from 24 MB to 213 MB (~9.2 MB/conn) and held it until the client exited. A real ~9.5 MB node binary at ~100 connections pins ~1 GB, OOM-killing keel-master on a 1-2 GB VPS; since no master supervisor is documented, the panel, subscriptions and node control channel stay down until manual restart. Filenames are fully guessable and path traversal is blocked by the char filter, so only valid keel-node-* names reach the fs.

**Reproduction.** python3 slow_dl.py opened 20 TLS conns (SO_RCVBUF 2048), each sent 'GET /dl/keel-node-linux-amd64' and never read: RSS 24272 KB -> 212704 KB during, flat at 212704 while held, 173712 after client exit. curl -sk /dl/keel-node-linux-amd64 => 200, size 10000000, with no cookie; missing file => cheap 404; /dl/etc-passwd and an encoded-traversal name => early 404.

**Fix.** Stream the file in download() with tokio::fs::File + tokio_util::io::ReaderStream into axum::body::Body::from_stream (or cache each dist file as an Arc<Bytes> keyed by name+mtime and clone per response) so per-connection memory is constant; add a tokio::sync::Semaphore cap on concurrent /dl transfers (503 when exhausted) and the write/idle timeouts from the U06 fix; optionally require the node bearer token for /dl.

## H2. No header-read/idle/write timeout and no connection cap on either listener; pre-auth /api/login buffers up to 2 MB/connection

- **Severity:** high · **Verdict:** confirmed · **Default config affected:** yes
- **Severity change:** medium -> high: the stalled-/api/login-body vector is an anonymous permanent OOM crash on the 1 GB-VPS target with no preconditions (bare master, same class as U05), and sustained idle-socket fd exhaustion is a full anonymous outage of the master (admin and nodes locked out); both reproduced. The pure fd-exhaustion reading alone is a recoverable (medium) outage, but the memory vector raises the issue to high.
- **Attacker:** anonymous-internet; one host, no auth. fd-exhaustion needs ~1000 cheap sockets (renewable); the login-body OOM needs ~500 held connections each fed ~1.9 MB once.
- **Locations:** `master/src/main.rs:286-296`, `master/src/main.rs:411`, `master/src/api.rs:133-143`, `master/src/api.rs:114`, `master/src/main.rs:276-283`

**Summary.** serve_tls (main.rs:286-296) spawns an unbounded task per accepted TCP connection; the only timeout is 10 s for the TLS handshake. hyper's http1::Builder gets no timer, so its default 30 s header_read_timeout is dropped (hyper-1.12.0 time.rs:75-78) and there is no idle/keep-alive/write timeout; grep confirms no .timer/header_read_timeout/DefaultBodyLimit/TimeoutLayer and no connection Semaphore in master/src (only VERIFYING). The axum::serve -no-tls path (main.rs:411) uses hyper_util auto::Builder with no timer either. The master does not raise RLIMIT_NOFILE and install.sh ships no master unit, so it runs under the default ~1024 soft limit. Two reproduced impacts: (1) idle post-handshake sockets accumulate until EMFILE and lock out admin and nodes, recovering only when released; (2) Json<Login> buffers up to the 2 MB axum default before login() runs (api.rs:137 before the locked_out check at 141), so stalled login bodies pin ~1.9 MB each with no body-read timeout, OOM-killing the master on a 1 GB VPS.

**Reproduction.** Under (ulimit -n 128) the master hit 'accept: Too many open files (os error 24)' x55 with ~115 idle TLS conns; a legit curl returned status 000 / exit 35 and recovered to 200 after release. 30 stalled POST /api/login bodies (Content-Length 2000000, ~1.9 MB sent then stalled) took RSS 21184->77088 KB (~1.8 MB/conn), held. A 2.2 MB body => connection reset (over the 2,097,152-byte axum-core DEFAULT_LIMIT); a 1.9 MB body is fully parsed (400).

**Fix.** In serve_tls build http1::Builder::new().timer(hyper_util::rt::TokioTimer::new()).header_read_timeout(~10s) and add a keep-alive idle timeout and an overall/write deadline; add a global and per-IP tokio::sync::Semaphore acquired before tokio::spawn so the connection count is bounded; put .layer(DefaultBodyLimit::max(4096)) on the /api/login route; mirror all of this on the axum::serve path (tower-http TimeoutLayer / RequestBodyTimeoutLayer); raise the soft RLIMIT_NOFILE at startup. The timer/cap half is shared with U05 and the master side of U07.

## H3. Default AnyTLS entries publish skip-cert-verify and authenticate with a replayable sha256(password) shared across every entry, so an on-path attacker steals a credential and reads all traffic

- **Severity:** high · **Verdict:** confirmed · **Default config affected:** yes
- **Severity change:** unchanged - MITM yields a reusable credential plus full plaintext in the out-of-the-box config, which the scale rates high (MITM -> secrets in the default setup); active on-path is explicitly in the project's threat model
- **Attacker:** network-mitm (active on-path: censor, ISP, public Wi-Fi) between a client and an AnyTLS entry; no credentials needed
- **Locations:** `master/src/sub.rs:73`, `master/src/sub.rs:195`, `master/src/sub.rs:244`, `master/src/sub.rs:340`, `master/src/sub.rs:384`, `master/src/db.rs:552-556`, `third_party/sing-anytls/client.go:35`, `third_party/sing-anytls/service.go:65-68`, `cmd/keel-node/cert.go:29-44`

**Summary.** A freshly created entry gets anytls_on=1, vless_on=0, no cert and no ACME (db.rs:552-556), so the node serves a self-signed cert and sub.rs:73 sets verify=false. I confirmed every format emits skip-cert-verify: true / "insecure": true / skip-cert-verify=true / insecure=1 and that all entries carry the same user.anytls_password (sub.rs:71). AnyTLS authenticates by sending sha256(password) as the first 32 bytes inside TLS (sing-anytls client.go:35, service.go:65-68) with no server nonce. I ran a TLS-terminating relay, captured those 32 bytes (= hashlib.sha256 of the user's password), and replayed them on a new connection to the real node: the server authenticated the stream, while a random 32-byte value hit the fallback and was dropped. Because clients skip verification there is zero server authentication and no pinning, so the attacker transparently terminates TLS, reads the credential plus every destination and payload, and later replays the credential on any of the user's entries.

**Reproduction.** Created entry via API -> anytls_on=1, anytls_acme=0, anytls_cert='' (confirmed in /api/state). Sub (clash/stash/singbox/surge/links) all emit skip-verify and password d8a16e77... on both entries. keel-node on 127.0.0.1:19412; scripts/mitm.py (ssl server cert CN=mitm.attacker.invalid) between auditclient (InsecureSkipVerify, as the sub instructs) and the node: client accepted the attacker cert, mitm captured first 32 bytes efcc5d40d3442dd0... == sha256('d8a16e77dee9eb3f3cf13b31e8104c77'). scripts/replay.py sent those 32 bytes + settings/SYN/PSH frames on a fresh TLS conn to the node -> server replied cmd 0x06 (cmdUpdatePaddingScheme, i.e. auth accepted); random hash -> 0 bytes ('unknown user password: fallback disabled' in node log).

**Fix.** In sub.rs proxies()/clash()/singbox()/surge()/share_links(): when verify is false, pin the node's self-signed cert by publishing its SHA-256 (mihomo fingerprint, sing-box certificate_public_key_sha256, Surge server-cert-fingerprint-sha256) using a value the node reports in certs; or default new entries (db.rs:552-556) to ACME/Reality and require an explicit visible opt-in before publishing unverified AnyTLS.

## H4. One report with up=i64::MAX overflows the SQL up+down sum to REAL, so load_world fails everywhere (panel, public page, every subscription, all config pushes) until manual SQL

- **Severity:** high · **Verdict:** confirmed · **Default config affected:** yes
- **Severity change:** unchanged (high): a compromised node causes a total, persistent master outage — the whole blast radius plus no recovery without manual SQL justifies high even though a node token is required.
- **Attacker:** Compromised node holding any one node token (e.g. a hostile VPS provider reading an entry's token from its config). One ~100-byte report frame after hello.
- **Locations:** `master/src/db.rs:528`, `master/src/db.rs:529`, `master/src/db.rs:575-583`, `master/src/app.rs:124-131`, `master/src/app.rs:56-64`, `master/src/db.rs:527`, `master/src/api.rs:291`, `master/src/sub.rs:447`, `master/src/db.rs:601-602`

**Summary.** on_report -> store_usage (app.rs:124-131, db.rs:575-583) upserts node-reported (name,period,up,down) with no ownership or range check. load_world computes `up+down` in SQL (db.rs:528) and reads column 3 as i64 (db.rs:529); when the sum overflows SQLite returns REAL and rusqlite yields InvalidColumnType, failing the whole call. load_world backs /api/state, /api/public, /s/{token}, App::sync (all config pushes), the DNS sync and exits' /api/node/ports, so every one of those fails. The poisoned row is keyed by the attacker's node id, kept when the node is deleted, and read for 70 days (db.rs:527), so it survives deletion, token rotation and restart; the admin can neither use the panel nor push a revocation to any node.

**Reproduction.** exp_u02.py vs the release master: before, state/public/sub(links+clash)=200. After one frame {"users":[{"name":"zz","period":"p","up":9223372036854775807,"down":1}]} (98 bytes): /api/state, /api/public, /s/<token>?format=links and ?format=clash all 500; exit's /api/node/ports returns 200 with empty body (its load_world fails). DB row shows typeof(up+down)='real'. PATCH disable alice, reset, and a new entry's initial push all fail to reach any node; delete node A -> 200 but row kept and all endpoints still 500; stop+start -> still 500; aged the row to 69 days -> still 500, to 71 days -> 200 (recovered). Log: repeated `api:`/`sync: load: Invalid column type Real at index: 3, name: up+down`.

**Fix.** One fix covers U02/U03/U04/U27-usage: in on_report/store_usage accept only counters the master pushed to that node (u<id> for users on that entry, n<entry>x<exit> for its own exits) and only the current/previous period, reject negatives and clamp up/down to <=2^50; compute the sum in Rust with i128/saturating_add instead of SQL `up+down` (or read up and down separately), and make load_world skip a row it cannot read rather than fail the whole world; purge a node's usage rows on delete_node and add a panel purge.

## H5. Pre-UUID VLESS addons parsing panics the whole keel-node (unbounded make in readAddons), reachable by any current or former subscriber once VLESS is enabled

- **Severity:** high · **Verdict:** confirmed · **Default config affected:** no
- **Severity change:** unchanged (high). Reproduced the pre-UUID panic directly; the only gate (Reality) is shared and non-rotatable. Kept at high for the persistent whole-node outage, while noting default_config_affected=false because VLESS is opt-in.
- **Attacker:** Anyone holding the entry's Reality parameters (public key + short id + SNI): every current subscriber, every removed/expired subscriber whose old vless:// link still works, and anyone a link leaked to. No valid UUID needed. Precondition: the admin enabled VLESS on the entry (vless_on=1); off by default.
- **Locations:** `cmd/keel-node/proto_vless.go:119`, `cmd/keel-node/inbound.go:53`, `$GOMODCACHE/github.com/sagernet/sing-vmess@v0.2.8-0.20250909125414-3aed155119a1/vless/protocol.go:96-105`, `$GOMODCACHE/github.com/sagernet/sing-vmess@v0.2.8-0.20250909125414-3aed155119a1/vless/service.go:56-60`, `master/src/db.rs:547`, `master/src/sub.rs:374-380`, `master/install.sh:56-62`

**Summary.** vless.Service.NewConnection runs ReadRequest (service.go:56) before the UUID lookup (service.go:60). ReadRequest copies the <=255-byte addons block and calls readAddons, which reads a protobuf uvarint flow length (protocol.go:96) and does make([]byte, flowLen) (protocol.go:100) with no upper bound; the seed field (protocol.go:107-111) has the identical bug. A 10-byte uvarint inside the 255-byte addons encodes up to 2^64-1, so make panics 'makeslice: len out of range' (or a mid-range value forces a multi-GB allocation -> OOM). keel calls this from `go serve(conn)` (inbound.go:53) with no recover anywhere on the path, so the panic aborts the entire process: every AnyTLS/VLESS/SS listener and all users drop. The Reality handshake is the only gate; its inputs (pbk/sid/sni) are one set per node (db.rs:547), identical for all users, embedded in every subscription link (sub.rs:374-380), and never rotated when a user is disabled or deleted. systemd Restart=always/RestartSec=3/StartLimitIntervalSec=0 (install.sh:56,61-62) makes a repeated crash a persistent outage.

**Reproduction.** Go test against the exact sing-vmess version keel uses (v0.2.8-0.20250909125414-3aed155119a1): configured user 'alice' with a real UUID, then fed bytes [0x00][16 zero bytes][addonsLen=11][0x0A then uvarint 0xFFFFFFFFFFFFFFFF] into svc.NewConnection over net.Pipe. Result: 'PANIC reproduced in vless.ReadRequest->readAddons (pre-UUID): runtime error: makeslice: len out of range'. The all-zero UUID is not the configured user, proving the panic precedes auth. grep for recover() in cmd/keel-node + third_party + sing-vmess/vless finds only a commented-out one (sing-anytls/session/session.go:171). TestAuditAcceptLoopEMFILE-style no-recover goroutine (inbound.go:53) means process abort.

**Fix.** Two independent fixes, either of which stops the process crash: (1) wrap every per-connection goroutine in a recover() that logs and closes the conn — in acceptLoop's `go serve(conn)` (inbound.go) and in the AnyTLS/mux stream callbacks — so a library bug kills one connection, not the node; this also covers U16. (2) Vendor sing-vmess and bound readAddons: reject flowLen/seedLen > uint64(reader.Len()) (and flow > ~64) before make, and do the userMap UUID lookup before parsing addons. Additionally set a read deadline on the Reality conn before RealityServer (covers U18), and give removed users a way to lose pre-auth access (per-user short id, or rotate the short id on user removal).

## H6. Guard treats Azure WireServer/HostGAPlugin 168.63.129.16 as public; on Azure nodes subscribers reach this root-only platform endpoint as uid 0

- **Severity:** high · **Verdict:** confirmed · **Default config affected:** yes
- **Severity change:** unchanged; scoped to Azure-hosted entries and exits; which secrets leak depends on the VM's extensions and deployed certificates
- **Attacker:** Any subscriber of an Azure-hosted entry whose traffic reaches direct (final or a rule), or of any entry routed to an Azure-hosted keel exit. Default config (allow_private=false; ipv4_only true or false).
- **Locations:** `cmd/keel-node/outbound.go:224-231`, `cmd/keel-node/outbound.go:239-248`, `cmd/keel-node/outbound.go:415`, `master/install.sh:58-63`, `master/install.sh:89-100`, `README.md:80`

**Summary.** isPublic only rejects addresses that are not global unicast, private, CGNAT or 0/8. 168.63.129.16 is Microsoft-owned public space, so the TCP Control hook and udpOutbound.WritePacket allow it, whether given as a literal or as a name that resolves to it. install.sh runs keel-node as root (no User=, no OpenRC command_user), so WALinuxAgent's firewall, which drops TCP to 168.63.129.16 for everyone except DNS and uid 0, does not stop it. A subscriber therefore gets WireServer (tcp/80: goal state, ExtensionsConfig, Certificates) and HostGAPlugin (tcp/32526). Per public research (Mandiant 2024, 'WireServing Up Credentials', AKS), a caller that supplies its own transport certificate receives the tenant certificates and can decrypt extension protectedSettings (VMAccess password/SSH-key resets, Custom Script secrets and SAS tokens, monitoring keys, Key Vault certificates deployed via osProfile.secrets); Azure DNS on :53 also passes. No other current major-cloud metadata endpoint passes the guard; the only other hit is legacy Oracle Cloud Classic 192.0.0.192 (see U65).

**Reproduction.** TestVFGuardTable (Control wrapped so connect is suppressed after the real guard; UDP through the real WritePacket on a closed socket), ipv4_only=false and true: 168.63.129.16:80 / :32526 / :53 -> isPublic=true, 'allow' in Control, UDP SEND. TestVFGuardNames: wire.test (fake DNS A 168.63.129.16) -> allow 168.63.129.16:80. Other cloud endpoints checked, all BLOCK/drop: IMDS 169.254.169.254, AWS 169.254.169.253 and 169.254.170.2, fd00:ec2::254, fd20:ce::254 (GCP), fd00:c1::a9fe:a9fe (OCI), fd00:42::42 and 169.254.42.42 (Scaleway), 100.100.100.200 (Alibaba), 100.80.80.80 (UCloud), 100.96.0.96 (Volcengine), 169.254.0.23 (Tencent). Only 192.0.0.192 (OCI Classic, legacy) and 161.26.0.10 (IBM classic service network, DNS/NTP only) also pass. install.sh:50-81 (systemd unit without User=) and :89-107 (OpenRC without command_user) confirm root. The Azure side (WireServer contents, waagent's uid-0 exemption) comes from Microsoft/WALinuxAgent documentation and public research; it was not tested here.

**Fix.** Give isPublic an explicit deny list of netip.Prefix values, starting with 168.63.129.16/32. Both userDialer's Control and udpOutbound.WritePacket call isPublic, so one change covers TCP and UDP, and the same list is the vehicle for U59/U65. As defense in depth, run keel-node as a dedicated user with AmbientCapabilities=CAP_NET_BIND_SERVICE so waagent's firewall applies. Do not use systemd IPAddressDeny for this address: the node's own resolver uses Azure DNS at 168.63.129.16:53.

## H7. The zone-wide Cloudflare DNS token is pushed to and cached on every ACME entry, although the panel says it stays on the master: one compromised entry controls the zone's DNS and can obtain trusted certificates for the panel and the other entries

- **Severity:** high · **Verdict:** confirmed · **Default config affected:** no
- **Severity change:** unchanged (high): once the feature is used, every ACME entry holds a zone-wide DNS-edit credential, and the panel tells the admin the opposite. Panel takeover needs the panel hostname in a zone the token covers; node takeover additionally needs a CA-cert or -no-tls master.
- **Attacker:** A compromised ACME-enabled entry (root on that VPS, e.g. a hostile provider), after the admin has set a Cloudflare token and turned on automatic certificates for that entry. Escalation to admin session theft needs the panel hostname in a zone the token can edit. Escalation to other nodes needs a master with a CA certificate or -no-tls (no pin in install commands).
- **Locations:** `master/src/nodecfg.rs:88-101`, `master/src/nodecfg.rs:213-214`, `master/web/app.js:850`, `cmd/keel-node/main.go:175`, `cmd/keel-node/acme.go:413-435`, `cmd/keel-node/acme.go:511-529`, `master/src/dns.rs:56-113`, `master/src/api.rs:203-213`, `master/src/main.rs:116-123`, `cmd/keel-node/master.go:254-273`, `cmd/keel-node/agent.go:373-421`, `docs/node-protocol.md:204`

**Summary.** nodecfg::acme() copies settings cf_token verbatim into inbounds[].acme.dns_token for every entry with anytls_acme and an SNI, and keel-node caches it in /etc/keel/node.json. The panel asks for Zone DNS Edit plus Zone Read and says the token is 'stored only on the master' (app.js:850). Cloudflare tokens are scoped per zone, not per record, and the node's own addTXT will write any name. So one compromised entry can rewrite or delete any record in the covered zones, which always include every ACME entry's name, and can obtain publicly trusted certificates (wildcards included) via DNS-01. If the panel hostname is in such a zone, the attacker repoints it, presents a valid certificate and reverse-proxies the master: the admin's Secure cookie and password are captured with no warning, which means full panel takeover. With -cert/-key or -no-tls masters, install commands carry no pin, so nodes and `agent update` trust WebPKI only. DNS control therefore also yields node tokens, arbitrary config pushes and root code execution through agent update. Tampered records persist, because dns.rs skips names cached as ok and refuses to touch records without the 'keel' comment.

**Reproduction.** Self-signed master on 127.0.0.1:19301: PATCH /api/settings {cf_token:'CF-ZONE-DNS-EDIT-TOKEN-verifyC-0123456789'}, then PATCH /api/nodes/1 {anytls_acme:true, anytls_sni:'jp.keel.test'}. My fake node using entry 1's token received acme={"challenge":"dns","dns_provider":"cloudflare","dns_token":"CF-ZONE-DNS-EDIT-TOKEN-verifyC-0123456789"}. Entry 2 (no ACME) and exit 3 got no token. The real keel-node binary (ACME and Cloudflare calls failed against a dead local proxy) cached it: node.json mode 0600, inbound acme {'challenge':'dns','dns_provider':'cloudflare','dns_token':'CF-ZONE-...'}; status.json holds only the URL and fingerprint. CA-cert master on 19303 (-cert/-key from a local CA): POST /api/nodes returned 'curl -fsSL https://panel.keel.test:19303/install.sh | sh -s -- --master https://panel.keel.test:19303 --token 43d3...', with no --fingerprint and no --pin. Code trace: master.go:254-257 verifies WebPKI only when the pin is nil; agent.go:373-405 builds the download client from the same tlsConfig and runs `<downloaded> agent version` as root before renaming it over itself and restarting. Not executed (no internet): Cloudflare record edits and DNS-01 issuance. The zone-wide reach follows from the requested permission and from acme.go:511-529, which creates records for whatever name it is given.

**Fix.** Stop sending cf_token to nodes. nodecfg::acme() should emit {"challenge":"dns","dns_provider":"master"}. Add a control message (node to master), e.g. {"type":"acme_dns","op":"set|clear","value":...}, handled in ws.rs/app.rs. The master derives the record name itself as "_acme-challenge." + that authenticated node's anytls_sni from its DB row, never from the message. It creates and deletes the TXT record with new dns.rs helpers (add_txt/delete_txt on top of the existing call()), with one pending record per node and an expiry. Alternatively, the master obtains certificates and pushes cert and key only to the owning node. Until then: correct the app.js:850 text, tell admins to rotate tokens already pushed, and recommend a token scoped to a dedicated zone reached by CNAME delegation of _acme-challenge. Independently, pin the master in install_command() for every TLS mode (an SPKI pin for -cert masters with key reuse, or a separate self-signed key for the node channel), and make agentUpdate() refuse to run without a pin or a binary signature.

## M1. Any node can write usage rows for any user and period (including users it does not serve, and negative values): block chosen users on every entry or lift quotas everywhere

- **Severity:** medium · **Verdict:** confirmed · **Default config affected:** yes
- **Severity change:** unchanged (medium): authenticated (node token) quota bypass / targeted user DoS / accounting falsification, no master takeover.
- **Attacker:** Compromised node holding one token — an entry that does not serve the target user, or an exit (which carries no user counters at all). User ids are small sequential integers and period labels are predictable dates.
- **Locations:** `master/src/db.rs:469-475`, `master/src/db.rs:575-583`, `master/src/nodecfg.rs:260-263`, `master/src/app.rs:124-131`, `master/src/nodecfg.rs:68-75`, `master/src/api.rs:362-375`, `master/src/sub.rs:472-473`

**Summary.** store_usage keys rows only by (reporting node, name, period) with no check that the counter belongs to that node (db.rs:575-583). World::used sums a counter name across all node ids (db.rs:469-475) and nodecfg pushes that sum, minus the receiving node, as used_base to every other entry (nodecfg.rs:260-263). A node can therefore report a large u<id> value to push used_base>=quota and block that user on every entry, or a large negative value to make the total <=0 (used_base then omitted) so the user gets quota times the number of entries. The exit-quota path is correctly scoped to the exit's own node (nodecfg.rs:68-75), but the user path is not. The lead side-note is also confirmed display-only: exits' health on the panel/public page comes from entries' reports (api.rs:362-375), so a compromised entry can mark other exits dead there without changing any other entry's routing.

**Reproduction.** exp_u04.py with a real keel-node as victim entry B: entry A (serving only carol) reported {"name":"u<bob>","up":10 GiB} -> panel showed bob 'over', entry C's pushed config carried used_base=quota, and the real node logged `user u1 blocked: quota used up`. Exit X (no user counters) reported 10 GiB for alice -> same block on B. A negative -1e15 from A drove bob's total to -999989799452672; used_base was omitted, the real node logged `user u1 unblocked`, and bob's subscription-userinfo header showed download=-999989799452672.

**Fix.** In on_report drop rows whose counter is not assigned to the reporting node and whose period is not the current/previous one, reject negatives and clamp. Same change as U02. Ignore user counters from exit-role nodes.

## M2. Node-controlled net_rx/net_tx deltas overflow node_month.rx into REAL, so /api/state and anonymous /api/public return 500 for the rest of the month

- **Severity:** medium · **Verdict:** confirmed · **Default config affected:** yes
- **Severity change:** unchanged (medium): breaks only /api/state and anonymous /api/public (not the data plane or subscriptions) and the admin can recover by deleting the node (node_month cascades), so it stays below U02.
- **Attacker:** Compromised node holding one token; a few report frames with crafted system.net_rx/net_tx.
- **Locations:** `master/src/app.rs:143-157`, `master/src/db.rs:586-593`, `master/src/db.rs:595-599`, `master/src/api.rs:292`, `master/src/db.rs:109`

**Summary.** on_report turns cumulative interface counters into deltas `drx = if rx>=prx {rx-prx} else {rx}` (app.rs:147) with no bound and no rejection of negatives, then add_node_month does `rx=rx+excluded.rx` in SQL (db.rs:589). That call writes usage rows for any counter name (U04) and recreates live state for a deleted node. Rotating the token or deleting the node, the admin's only revocation tools, therefore cannot stop U04-style quota tampering by a connection that is already up. ## M21. IPv4-embedding IPv6 forms (64:ff9b::/96, 64:ff9b:1::/48, 2002::/16, ::/96, ::ffff:0:0:0/96, Teredo) pass the guard with private or metadata IPv4 inside

## I14. IPv6 exit addresses are written to entry configs without brackets, so entries cannot reach IPv6-connected exits

## Refuted

**A hello whose config_rev equals the stored rev suppresses the initial config push (benign)** — refuted. on_hello (app.rs:99-122): when a node's hello.config_rev equals the DB's stored rev (>0), the master adopts the stored hash/shape and does not force a push. This is the normal in-sync case. sync() (app.rs:56-95) still pushes whenever the freshly computed config hash differs from the stored hash, so any edit — including edits made while the node was offline — still reaches the node on reconnect. A node that lies about its rev gains nothing because a compromised node can disregard pushed configs anyway, and a rolled-back honest cache reports a mismatching rev and is corrected.

*Reproduction:* exp_u29_u34_u80.py: node D reconnecting with a matching rev and no intervening edits received no push (correct). After an admin added a user while D was offline, D reconnecting with the OLD rev DID receive a config containing the new user (hash differs -> sync pushes). keel-node writes the master rev into its cached config (main.go:155-183), so after a restart it reports the true cached rev.
